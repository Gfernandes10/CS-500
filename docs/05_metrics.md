# Metrics and Evaluation

## Objective

Provide a repeatable metrics pipeline for command, telemetry, video, GUI, recovery, keepalive, link-quality, and RC-control evaluation. The metrics layer exists so CLI runs, Control Panel runs, and future ROS/control use cases can be compared with one schema.

## Experiment and Analysis Workflow

1. Development and diagnostic procedures are defined in [08_experiments.md](08_experiments.md).
2. The statistically repeated final protocol is defined in [09_final_repeated_experiment_protocol.md](09_final_repeated_experiment_protocol.md).
3. Final figures and quantitative summaries are generated with [final_experiment_analysis.ipynb](../notebooks/final_experiment_analysis.ipynb).
4. Generated report figures are saved under [docs/images](images/).
5. The final report uses a curated experiment set from [results](../results/), not every diagnostic/demo CSV that may be present in the directory.

## Current Implementation

1. `MetricsCollector` is the central runtime metrics aggregator.
2. CLI command-watch, CLI state-watch, CLI video-watch, and Qt Control Panel exports use the central CSV schema.
3. Standalone `tello_viewer` is retired from the active build surface; video/runtime metrics live in the CLI diagnostics and Qt Control Panel.
4. FFmpeg Stream is the only active video runtime path. Video exports contain FFmpeg transport, decoded-frame, decode-error, frame-size, FPS, and freshness fields; the retired NAL assembly schema is no longer exported.
5. GUI-visible log messages are also written into the metrics CSV with timestamps, allowing event rows to be correlated with telemetry, command, RC, and video behavior.
6. State recording uses a separate state CSV that includes telemetry samples and recorded RC command samples on the same monotonic recording timeline.

## CSV Export Entry Points

### CLI Command Watch

```bash
./build/tello_cli --watch \
  --interval-ms 1000 \
  --duration-s 120 \
  --metrics-csv ../results/E2-CMD-BASE-001.csv \
  --test-id E2-CMD-BASE-001 \
  --scenario command-baseline \
  --notes "Tello idle on desk; command baseline"
```

### Qt Control Panel

The Control Panel records GUI metrics and state history through the Logging Export Configuration section. The user sets the metrics CSV path and state CSV path, starts recording, performs the run, stops recording, and exports both CSV files.

## Central MetricsCollector Schema

The active exports use the header generated by `MetricsCollector::toCsvHeader()`.

Major field groups:

1. experiment metadata (`test_id`, `scenario`, `notes`, `run_mode`);
2. runtime index (`elapsed_ms`, `attempt`);
3. command metrics, including latency, latest command/result/response, retry counts, internal attempt logs, recovery timing, and mutex wait diagnostics;
4. telemetry receiver stats, packet age, interarrival gaps, and telemetry quality;
5. FFmpeg video transport/decode stats, frame size, decoded FPS, errors, and video quality;
6. recovery/event/connection-state fields;
7. keepalive state and counters;
8. RC stream/keyboard state and latest RC values;
9. GUI timing, display counters, and plot timing;
10. aggregate link quality (`link_quality`, `link_quality_score`, `link_safe_for_nonzero_rc`, and component labels);
11. timestamped log/event rows.

## Quality Labels

The word "quality" means transport freshness and continuity. It does not mean subjective video sharpness, scene visibility, or flight-control accuracy.

Telemetry and video labels use these thresholds:

1. `OK`: latest packet/frame age <= 200 ms and interarrival <= 300 ms.
2. `DEGRADED`: latest packet/frame age <= 500 ms and interarrival <= 500 ms.
3. `STALE`: data is older than those limits.
4. `NO_DATA`: no packet/frame has arrived.

`packet age` is how old the newest available packet/frame is when a metrics row is written. `packet interarrival` is the time gap between consecutive received packets/frames.

## Aggregate Link Quality For Control

`MetricsCollector` computes a reusable link-quality snapshot in the core library. The same concept is displayed in the Qt Control Panel and published by the ROS driver as `/tello/link_quality`.

The aggregate quality combines:

1. telemetry freshness and interarrival timing;
2. video freshness when video is active;
3. command/keepalive health;
4. RC send cadence while RC streaming or keyboard control is active.

Labels:

1. `OK`: data is fresh and packet/frame spacing is within expected bounds.
2. `DEGRADED`: data is still usable, but recent spacing or command recovery indicates reduced margin.
3. `STALE`: the latest data is too old for confident control decisions.
4. `BLACKOUT`: active RC has a long packet gap, which is unsafe for sustained nonzero RC.
5. `NO_DATA`: no relevant samples have been received yet.

The field `link_safe_for_nonzero_rc` is a conservative control hint. A controller can use it to decide whether nonzero RC commands are allowed. If it is false, safer behavior is to reduce command magnitude, send neutral `rc 0 0 0 0`, hover, land, or abort depending on the operating mode. This field does not replace controller-specific safety logic; it provides a shared signal so GUI, CLI, and ROS components can react consistently to link degradation.

## Validation Performed

1. CLI command, telemetry, and video exports generated central-schema CSV rows.
2. The Control Panel exported GUI metrics and state recording CSVs.
3. The final notebook generated report figures from the curated real-drone experiment set.
4. Command diagnostics separated normal low-latency samples from recovered transient outages.
5. Telemetry and video quality plots used freshness/continuity thresholds.
6. Keyboard RC analysis correlated RC samples with state recording timestamps.
7. Link-quality fields were exposed for GUI display and ROS publication.
